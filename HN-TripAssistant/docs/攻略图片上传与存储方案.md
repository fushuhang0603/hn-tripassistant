# 攻略图片上传与存储方案（中间表版）

> 适用模块：HN-TripAssistant 攻略广场（Guide）
> 方案形态：形态 A——纯文本正文 + 文末图集（图片统一排在正文末尾，不图文穿插）
> 存储决策：图片记录走 `guide_image` 中间表（而非 guide 表 JSON 字段），图片文件存阿里云 OSS，数据库只存 URL

## 1. 背景与决策

### 1.1 为什么用中间表

| 考量点 | 结论 |
|---|---|
| 图片独立身份 | 有独立 id，单张可删除/替换，为将来图片审核、元数据（宽高、AI 描述）留扩展空间 |
| 数据规范化 | 满足 1NF，不解析字符串 |
| 孤儿文件清理 | 将来做"OSS 上有图但帖子已删"的清理时，可精确列出帖子图片 URL |
| 代价 | 发布时事务两步写、详情多一次查询，开发量略增，可接受 |

### 1.2 为什么不用 JSON 字段 / 逗号分隔

- 逗号分隔：URL 理论上可能含逗号（签名参数），有歧义风险
- JSON 字段：图片无独立身份，将来单独管理要改结构 + 迁移存量数据

## 2. 数据模型设计

### 2.1 guide 表（不变）

`guide` 表保持现状，**不新增 images 字段**。封面 `cover` 仍存 guide 表。

### 2.2 新增 guide_image 表

```sql
create table guide_image (
    id          bigint unsigned not null auto_increment comment '主键',
    guide_id    bigint unsigned not null comment '攻略ID',
    url         varchar(512)    not null comment '图片完整URL',
    sort        int             not null default 0 comment '图集内顺序，从0开始',
    create_time datetime        not null default current_timestamp comment '创建时间',
    primary key (id),
    key idx_guide_id (guide_id)
) engine = InnoDB default charset = utf8mb4 comment = '攻略图集表';
```

要点：
- `sort` 记录图集展示顺序，详情查询 `order by sort asc`
- 图片数量上限 9 张（Service 层校验，不在 DB 层做）
- 帖子删除时级联删除该表记录（将来做删除接口时一并处理）

## 3. 图片上传流程（先上传，后发布）

### 3.1 上传链路

```
前端选图
  → POST /api/guide/upload（multipart/form-data，file 字段）
  → 后端校验（类型白名单 jpg/jpeg/png/webp，大小 ≤ 5MB）
  → 上传 OSS：对象路径 guide/{yyyyMMdd}/{uuid}.{ext}
  → 返回完整 URL（https://bucket.endpoint/guide/...）
  → 前端把 URL 暂存编辑器状态（缩略图预览）
```

### 3.2 OSS 配置

- `application.yaml` 增加：

```yaml
aliyun:
  oss:
    endpoint: oss-cn-xxx.aliyuncs.com      # 按 Bucket 地域填
    access-key-id: ${OSS_ACCESS_KEY_ID}    # 环境变量注入，禁止明文提交
    access-key-secret: ${OSS_ACCESS_KEY_SECRET}
    bucket: your-bucket-name

spring:
  servlet:
    multipart:
      max-file-size: 5MB
      max-request-size: 30MB
```

- 新增 `OssConfig` 配置类：注册 `OSSClient` Bean（依赖已引入：aliyun-sdk-oss 3.18.5）
- 上传方法接收 `MultipartFile`：校验 → 生成对象路径 → `putObject` → 返回 URL

### 3.3 孤儿文件说明（已知代价，第一版不做处理）

用户上传了图片但放弃发布 → OSS 上残留孤儿文件。第一版量小不处理；将来可用"扫描 OSS 目录对比 guide_image 引用"的方式清理，这正是中间表方案的收益点之一。

## 4. 发布流程（事务两步写）

`publish` 在同一个事务里完成：

1. 校验：标题/城市/正文非空；images 数量 ≤ 9
2. `insert guide`（useGeneratedKeys 回填 id）
3. `images` 非空时，批量插入 `guide_image`：
   - `guide_id` = 刚回填的 id
   - `sort` = 数组下标
   - AI 一键发布（source=AI_TRIP）时 images 为空，跳过本步
4. **封面兜底**：`cover` 为空时取 `images[0]` 作为封面（避免前端重复传）

## 5. 详情查询流程

新增 `GET /api/guide/detail/{id}` 链路（当前项目只有 publish / page 两个接口）：

1. 查 `guide` 主体：新增 `selectById`
2. 查图集：`select url from guide_image where guide_id = ? order by sort asc` → `List<String>`
3. 组装 `GuideDetailVO`：
   - 现有字段照旧
   - 新增 `images`（List<String>）
   - `liked` 字段：点赞功能未做前返回 `false` 占位，做了点赞后查 `guide_like` 表补上

列表 `pageSelect` **不查图片**（卡片只看 cover），保持查询轻量。

## 6. 接口清单

| 接口 | 说明 |
|---|---|
| `POST /api/guide/upload` | 单张图片上传，返回 `Result<String>`（图片 URL），需登录 |
| `POST /api/guide/publish`（改） | DTO 新增 `images: List<String>`；事务内写 guide + guide_image |
| `GET /api/guide/detail/{id}`（新） | 详情：正文 + 图集 + 作者 + 点赞状态 |

## 8. 前端配合流程

```
发布弹窗：
  正文 textarea + "添加图片"按钮
  → 选图 → 逐张调 /api/guide/upload → URL push 进 images 数组，缩略图预览
  → 发布时一次 POST /api/guide/publish（images 为 URL 数组）

详情页：
  调 /api/guide/detail/{id}
  → 渲染正文文本
  → 遍历 images 渲染文末图集（九宫格/瀑布流）
```

## 9. 边界与待办

1. **孤儿文件清理**：第一版不做，将来扫描 OSS 目录对比 guide_image 引用
2. **帖子删除**：将来做删除接口时，事务内级联删 guide_image 记录
3. **liked 状态**：点赞功能上线后，detail 里查 guide_like 表补真值
4. **图片压缩**：第一版原图直传，将来可加缩略图/压缩（OSS 图片处理或前端压缩）

## 10. 实施顺序

1. 建表 `guide_image`
2. 实体/DTO/VO 字段 + Mapper（GuideImageMapper + selectById）
3. publish 事务两步写 + cover 兜底
4. 上传接口（OssConfig + application.yaml + upload 方法）
5. 详情接口链路
6. 前端：发布弹窗图片选择 + 详情页图集渲染
