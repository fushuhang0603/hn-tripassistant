# 意图识别架构设计

> 记录日期：2026-09-09
> 状态：设计阶段（待实现）
> 关联文档：`AI行程规划业务流程.md`（行程规划主链路）

---

## 一、背景与目标

海南深度游 AI 助手需要从「单次问答」升级为「多轮智能体」，解决三个问题：

1. **意图杂**：用户输入覆盖行程规划、天气、机票/交通、景点美食、政策问答、闲聊等；
2. **多轮失忆**：无状态调用导致追问后丢失已收集参数；
3. **入口散**：当前 `GraphController` 中 `/extractParam`、`/planTrip` 裸调图，前端难对接。

目标：以 **IntentRecognizer（意图识别器）+ Handler（可插拔执行器）** 为核心，统一入口、多轮持久化、能力可扩展。

## 二、架构总览

```
用户消息
   │
   ▼
ChatController (/api/chat/send)        统一入口
   │
   ▼
ChatService ── SessionManager.load(sessionId) ──▶ ChatContext
   │
   ▼
IntentRecognizer.recognize(message, context)
   │  ① 规则引擎（纯文本规则，高置信短路，0 token）
   │  ② LLM 分类器（未命中时，结构化输出）
   │
   ▼
IntentResult { intent, confidence, slots }
   │
   ▼
HandlerDispatcher.dispatch(intent)
   │  从 HandlerRegistry 找到对应 Handler，未注册/低置信降级 GeneralHandler
   ▼
┌───────────────── Handler 列表 ─────────────────┐
│ TripPlanningHandler   行程编排 Agent（多步）     │
│ TransportSearchHandler 交通方式查询              │
│ HotelSearchHandler    住宿查询（高德 MCP）        │
│ WeatherHandler        天气查询（高德 MCP）        │
│ POISearchHandler      景点/美食（高德 MCP）       │
│ PolicyHandler         政策问答（知识库 RAG）      │
│ RagHandler            攻略检索（知识库 RAG）      │
│ GeneralHandler        闲聊回复（纯 LLM）          │
└────────────────────┬────────────────────────────┘
                     ▼
SessionManager.save（写回 Redis 快照 + 消息历史）
                     ▼
ChatResponse { sessionId, intent, reply, askMessage, data }
```

设计原则：

- **识别器统一**：所有输入先过 IntentRecognizer，Handler 不各自解析意图；
- **Handler 可插拔**：新增能力 = 新增一个 `IntentHandler` 实现类，主链路零改动；
- **会话独立成基础设施**：SessionManager 不绑定任何具体 Handler，追问循环通用；
- **便宜判断先行**：规则引擎最靠前，能短路就短路，省 token、省延迟。

## 四、IntentRecognizer（意图识别器）

```java
public interface IntentRecognizer {
    IntentResult recognize(String message, ChatContext context);
}

public class IntentResult {
    private IntentType intent;
    private double confidence;              // 置信度 0~1
    private Map<String, Object> slots;      // 预提取槽位：city/days/date/keyword...
    private boolean needContext;            // 是否依赖会话状态
}
```

### 4.1 规则段（IntentRuleEngine）

- 采用 AC 多模式匹配（Aho-Corasick），一次扫描同时命中关键词 + 正则；
- 命中且置信度 ≥ 0.9 时短路，不调 LLM；
- 规则可配置（yaml / DB 表），上线后免发版调整。

初始规则示例（海南高频词）：

| 规则 | 模式 | 意图 | 直接抽取槽位 |
|---|---|---|---|
| `规划\|安排\|行程\|玩.*天` | AC | TRIP_PLANNING | days、city |
| `机票\|航班\|怎么去.*海口` | AC | TRANSPORT_SEARCH | from/to/date |
| `酒店\|民宿\|住哪` | AC | HOTEL_SEARCH | city |
| `天气\|台风\|下雨` | AC | WEATHER | city |
| `免税\|离岛` | AC | POLICY_QA | — |
| `算了\|不用\|取消` | AC | GENERAL（取消语义） | — |

### 4.2 LLM 段（LLMIntentClassifier）

规则未命中时，一次 LLM 调用输出结构化结果（`BeanOutputConverter`，与现有 `ExtractParamNode` 同套路）：

```json
{
  "intent": "ASK_WEATHER",
  "confidence": 0.92,
  "slots": { "city": "三亚", "date": "2026-10-03" },
  "needTool": true,
  "toolName": "weather"
}
```

Prompt 要点（直接写死，防误判）：

- 明确区分三类场景：**新建任务 / 回应追问 / 调整已有行程**；
- 注入当前 `phase`，phase=COLLECTING 时优先判定「回应追问」。

### 4.3 降级策略

- 置信度 < 0.5 → 强制降级 GENERAL；
- Handler 执行异常 → 捕获后回 GENERAL 兜底回复 + 记日志，不向用户暴露 500。

## 五、Handler 路由层

### 5.1 策略接口

```java
public interface IntentHandler {
    IntentType support();                  // 声明承接的意图
    HandlerResult handle(ChatContext context);   // 执行
}
```

Spring 启动时收集所有 Handler Bean 进 `HandlerRegistry`，形成 `Map<IntentType, IntentHandler>`。

### 5.2 Handler 清单

| Intent | Handler | 能力来源 | 步骤数 |
|---|---|---|---|
| TRIP_PLANNING | TripPlanningHandler | 内部多步 Agent | 多步 |
| TRANSPORT_SEARCH | TransportSearchHandler | 高德 MCP（交通）+ 机票 Provider 接口 | 单步 |
| HOTEL_SEARCH | HotelSearchHandler | 高德 MCP（住宿搜索） | 单步 |
| WEATHER | WeatherHandler | 高德 `maps_weather` | 单步 |
| POI_SEARCH | POISearchHandler | 高德 text/around/detail | 单步 |
| POLICY_QA | PolicyHandler | 政策知识库 | 检索+LLM |
| RAG_QA | RagHandler | 攻略知识库 | 检索+LLM |
| GENERAL | GeneralHandler | 纯 LLM（海南人设 prompt） | 单步 |

### 5.3 TripPlanningHandler（行程编排 Agent，重点）

内部顺序编排五步：

```
context.extractParam（含历史合并参数）
   → Step1 参数完整性检查 ── 缺参 → 返回追问（complete=false, askMessage）
   → Step2 行程骨架生成（LLM）
   → Step3 地理补全（MCP 搜索 POI）
   → Step4 餐饮/路线优化（MCP）
   → Step5 校验 → 写回 tripPlan 快照
```

> 实现选择（待确认）：
> - 方案 A：继续用 LangGraph 编图，Handler 仅一次 `invoke`；
> - 方案 B：不用图框架，Handler 内顺序编排五个 Step（接口 + 责任链）。
> 倾向 B：Handler 范式下顺序编排足够，图的 Checkpoint 能力由 SessionManager 取代，架构统一。

### 5.4 TransportSearchHandler（交通方式，机票预埋接口）

```java
public interface FlightSearchProvider {   // 抽象供应商
    List<FlightOption> search(String from, String to, String date);
}
// 实现1：MockFlightSearchProvider（开发期假数据）
// 实现2：携程/飞猪开放平台（后续接入，不动 Handler 和主链路）
```

本期先落地高德交通查询（路径规划：三亚↔海口、机场到酒店），机票留 provider 接口位。

### 5.5 知识库检索（Policy / Rag 共用）

渐进式落地：

- **P0**：攻略表（MySQL）+ 关键词检索 + LLM 整理回答，零新依赖；
- **P1**：Spring AI Alibaba VectorStore（DashScope Embedding + 向量库），攻略广场内容、海南免税政策文档切片入库。

两个 Handler 共用 `KnowledgeBaseService`，仅检索的知识库集合不同（policy 库 / guide 库）。

## 六、会话持久化（Redis）

### 6.1 选型结论

会话数据特征（读写高频、24h 过期即废弃、可容忍丢失）与 Redis 高度契合，采用 **Redis 热层 + MySQL 冷归档（可选）**。

### 6.2 Key 设计

```
chat:session:{sessionId}      String(JSON)  会话快照：phase/intent/extractParam/tripPlan/userId
                              TTL 24h，每次读写刷新
chat:history:{sessionId}      List          消息历史：LPUSH 新消息，LTRIM 保留最近6条
                              TTL 24h
chat:index:{userId}           Set           用户 → sessionId 索引（历史会话列表，可选）
```

`chat:session:{sessionId}` 示例：

```json
{
  "sessionId": "a1b2c3",
  "userId": 1,
  "phase": "COLLECTING",
  "intent": "TRIP_PLANNING",
  "extractParam": { "cities": ["三亚"], "days": 5, "person": null },
  "tripPlan": null,
  "updateTime": "2026-09-09T10:00:00"
}
```

### 6.3 存储抽象

```java
public interface SessionStore {
    ChatSession load(String sessionId);
    void save(ChatSession session);
    void appendMessage(String sessionId, ChatMessage msg);
    List<ChatMessage> recentMessages(String sessionId, int n);
}

@Component
public class RedisSessionStore implements SessionStore {
    // StringRedisTemplate + Jackson 手动序列化
    // 读后 EXPIRE 刷新 TTL，保持活跃会话不过期
}
```

- 序列化用 **Jackson JSON**，不用 JDK 原生序列化；
- 不引入 Spring Session（那是 HTTP Session 共享，与业务对话状态无关）；
- MySQL 归档可选：如需「历史会话列表」功能，用 `@Async` 异步写 `chat_message` 表，失败不影响主流程。

### 6.4 会话状态机

```
IDLE ──TRIP_PLANNING──▶ COLLECTING ──参数齐全──▶ PLANNING ──成功──▶ PLAN_DONE
 ▲                         │                            │
 │                    回应追问（合并槽位）                │
 │                         │                            │
 └──CANCEL─────────────────┴────────────────────────────┘
PLAN_DONE ──调整意图──▶ PLANNING（带旧 tripPlan + 修正指令重跑）
```

### 6.5 参数合并（追问不失忆的关键）

```
新槽位 = merge(历史 extractParam, 本轮提取槽位)   // 新值覆盖，null 不覆盖
```

例：首轮「三亚5天」，追问「几个人？」，用户答「3个」→ 合并后 `{cities:[三亚], days:5, person:3}`。

### 6.6 上下文注入策略

每次请求拼装 prompt 上下文只注入三样：

1. 最近 N 条消息（N=6，超出的只留摘要）；
2. `extractParam` 快照（结构化，约 200 token）；
3. 当前 `phase + intent`（1 行，防 LLM 误判「回应追问」为「新建任务」）。

## 七、关键机制

### 7.1 意图切换（追问态救场）

当 phase=COLLECTING（正在追问）时：

- 用户输入「算了」→ 规则段命中取消 → 结束当前任务，phase 回 IDLE；
- 用户插问新问题（如「三亚天气怎么样」）→ 识别出 WEATHER，先响应新问题，追问状态挂起不丢（快照在 Redis）。

### 7.2 统一入口

```java
@PostMapping("/api/chat/send")
public ChatResponse chat(@RequestBody ChatRequest req) {
    // 1. SessionManager.load  → ChatContext
    // 2. IntentRecognizer.recognize
    // 3. HandlerDispatcher.dispatch
    // 4. SessionManager.save（快照 + 历史）
}
```

请求/响应结构（前端 `request.ts` 一次对接）：

```java
public class ChatRequest {
    private String sessionId;   // 首次为空，后端创建后返回
    private String message;
}

public class ChatResponse {
    private String sessionId;   // 前端始终带回来
    private IntentType intent;
    private boolean complete;   // 编排类：参数是否齐全
    private String reply;       // 自然语言回复（always 有）
    private String askMessage;  // 追问文案
    private Object data;        // 结构化数据：tripPlan / flights / weather / pois
}
```

## 九、实施顺序

1. `model` + `IntentHandler` + `HandlerRegistry` + `GeneralHandler`（最小可跑链路）；
2. Redis 接入 + `SessionStore` + `SessionManager`（多轮能力底座）；
3. `IntentRecognizer`（规则段 + LLM 段）；
4. 四个查询 Handler（Transport / Hotel / Weather / POI，Transport 先走交通）；
5. `TripPlanningHandler`（顺序编排五步，接追问循环）；
6. `KnowledgeBaseService` + Policy / Rag Handler（P0 关键词检索）；
7. 前端切换统一入口 `/api/chat/send`。
